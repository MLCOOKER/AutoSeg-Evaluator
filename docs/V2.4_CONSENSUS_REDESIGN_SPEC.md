# v2.4 — Multi-Observer Consensus Redesign (Implementation Spec)

_Status: **implemented**, shipped across v2.4.0 to v2.4.2 (June 2026). Written 2026-05-27, before the work began; kept as the record of what was decided and why. Line references point at the code as it stood then and have drifted since._

This document specifies the v2.4 redesign of the multi-observer STAPLE
consensus workflow (Tab 1 source labels + Tab 2 Build Consensus GT). It is
the contract for implementation — file-by-file changes, data-model
additions, the new grouping logic, UI behaviour, and the testing plan.

---

## 1. Motivation

The current Build Consensus GT tab (Tab 2) has two automatic-only decisions
the user cannot override:

1. **Grouping** — RTSSes are grouped by `(patient_id, source_label)`; a group
   forms only when 2+ RTSSes share the *exact same* source label
   ([`_eligible_groups`](../src/autoseg_evaluator/ui/tabs/build_consensus.py#L433)).
2. **Organ matching** — ROIs are clustered by fuzzy name similarity with no
   manual correction; failures are uncorrectable except by nudging a global
   threshold ([`_auto_match_group`](../src/autoseg_evaluator/ui/tabs/build_consensus.py#L458)).

For a **multi-observer manual contouring study** (several clinicians each
contour the same cohort), this breaks down:

- Observers' RTSSes may not share a source label, so no group forms.
- Even when grouped, the per-rater inter-observer matrix labels raters by
  **filename** ([`build_consensus.py:1063`](../src/autoseg_evaluator/ui/tabs/build_consensus.py#L1063)),
  which is non-distinguishing when all files came from one TPS.
- Fuzzy organ matching has no manual override.

### Design decisions (locked)

| Topic | Decision |
|---|---|
| Rater identity | **The source label IS the rater identity.** Each observer gets a distinct source label, assigned once in Tab 1; it persists per-SOP-UID and is consistent across all patients by construction. |
| Grouping | Tab 2 grouping **inverts**: the user selects which source labels are "observers"; each patient's consensus group = its RTSSes whose label ∈ the selected observer set. One consensus per patient. |
| Identifying observers | Tab 1 source-labels window gains `ReviewerName`, `OperatorsName`, and parent-folder columns + **assisted propagation** (a "Select similar" helper feeding the existing bulk-override). |
| Organ matching | **Editable drawers** (drag ROIs between buckets) + a visible **unmatched tray**; manual edits **lock the group** from threshold re-clustering. |
| Per-patient view | Kept. |

### Why this is simpler than a separate rater registry

Rater identity reuses the existing source-label mechanism, which is already
(a) persisted in `settings.json` keyed by SOPInstanceUID
([`utils/settings.py:47`](../src/autoseg_evaluator/utils/settings.py#L47)),
(b) displayed everywhere, and (c) editable via the Manage Source Labels
dialog. No new identity concept, no token-detection subsystem. Cross-patient
consistency is guaranteed because the user assigns the same label to a given
observer's files on every patient.

## 2. Conceptual model

```
Tab 1 (Manage Source Labels)
  └── assign a DISTINCT source label per observer
        e.g.  Observer A, Observer B, Observer C
        (assisted propagation makes this fast across patients)

Tab 2 (Build Consensus GT)
  └── user selects which source labels are "manual observers"
        {Observer A, Observer B, Observer C}
  └── per patient: group = RTSSes whose label ∈ selected observers
  └── organ-match within the group (editable + unmatched tray)
  └── generate ONE synthetic STAPLE consensus per patient
        raters in the inter-observer matrix are labelled by source label
```

A mixed cohort (AI vendors + manual observers) is fine: the source-label
column will hold a mix (`Limbus`, `MIM`, `Observer A`, `Observer B`), and the
Tab 2 observer-selection is what designates which labels are observers.

**Deliberate simplification:** one consensus group per patient (the selected
observers). Two separate consensuses per patient from different label sets is
out of scope.

## 3. Phase 1 — Tab 1 (source-label window)

### 3.1 Data-model additions

**File:** [`src/autoseg_evaluator/data/metadata.py`](../src/autoseg_evaluator/data/metadata.py)

Extend `RTSTRUCTEntry` (currently ends at the v2.3 fields) with two more
optional raw-DICOM fields:

```python
@dataclass
class RTSTRUCTEntry:
    # … existing fields …
    structure_set_description: str = ""
    manufacturer_model_name: str = ""
    # ── v2.4 additions ──
    reviewer_name: str = ""        # (300E,0008) RT Approval module
    operators_name: str = ""       # (0008,1070) General Equipment / Series

    @property
    def parent_folder(self) -> str:
        """Name of the directory the RTSS file lives in (PHI-safe display
        token used to help identify observers). Empty for synthetic."""
        if self.is_synthetic_consensus or not self.file_path:
            return ""
        return os.path.basename(os.path.dirname(self.file_path))
```

`parent_folder` is a derived property (no new stored state) so it needs no
scanner change. `reviewer_name` / `operators_name` are populated in the
scanner.

**Scanner population** — [`metadata.py` `_add_rtstruct`](../src/autoseg_evaluator/data/metadata.py#L291):

```python
RTSTRUCTEntry(
    # … existing …
    manufacturer_model_name=_get_str(ds, "ManufacturerModelName"),
    reviewer_name=_get_str(ds, "ReviewerName"),
    operators_name=_get_str(ds, "OperatorsName"),
)
```

Both default to `""`, so older sessions / tests / synthetic-consensus
constructors load unchanged (same backward-compat pattern as v2.3).

### 3.3 Assisted propagation ("Select similar")

Implemented as a **selection helper that feeds the existing bulk-override**,
not a parallel mechanism. The bulk-apply row
([`source_labels.py:170`](../src/autoseg_evaluator/ui/dialogs/source_labels.py#L170))
is preserved unchanged; propagation just auto-populates the table selection.

**Behaviour:**

1. User assigns (or selects) one row.
2. A new **"Select similar…"** button (next to "Bulk apply") inspects that
   row's distinguishing fields, in priority order:
   `parent_folder → operators_name → reviewer_name → structure_set_name →
   manufacturer → filename-stem`.
3. For the first field with a **non-empty** value, find all other rows sharing
   that exact value. Pop a small confirmation:
   _"4 other files share OperatorsName = 'JK'. Select them?"_
   with the field name + value shown so the user knows what's being matched.
4. On confirm, those rows are added to the table selection. The user then
   types a label and clicks the existing **Apply** — labelling all selected
   rows in one action.

**Implementation sketch:**

```python
def _on_select_similar(self) -> None:
    rows = self._selected_data_rows()
    if len(rows) != 1:
        self._toast("Select exactly one row first, then 'Select similar'.")
        return
    anchor = rows[0]
    rtss = self._rtss_for_row(anchor)
    field, value = self._best_distinguishing_field(rtss)   # cascade above
    if not value:
        self._toast("No distinguishing metadata on the selected file.")
        return
    matches = [r for r in range(self._table.rowCount())
               if self._field_value(r, field) == value]
    if len(matches) <= 1:
        self._toast(f"No other files share {field} = '{value}'.")
        return
    if self._confirm(f"{len(matches) - 1} other files share "
                     f"{field} = '{value}'. Select them?"):
        self._select_rows(matches)
```

The field-cascade lives in a small pure helper so it's unit-testable without
Qt. **Bulk override is kept** — "Select similar" is additive.

### 3.4 Phase 1 tests

  when both present; falls through to filename when all metadata empty.

## 4. Phase 2 — Tab 2 (observer selection + grouping inversion)

**File:** [`src/autoseg_evaluator/ui/tabs/build_consensus.py`](../src/autoseg_evaluator/ui/tabs/build_consensus.py)

### 4.1 Observer-selection UI

Add a top panel above the eligible-groups list:

```
┌─ Manual observers ─────────────────────────────────────────┐
│ Select the source labels that represent manual observers.  │
│ [✓] Observer A    [✓] Observer B    [✓] Observer C         │
│ [ ] Limbus        [ ] MIM                                   │
│  (each checked label becomes a rater in the consensus)      │
└────────────────────────────────────────────────────────────┘
```

- A checkable list / flow of every distinct non-synthetic source label in the
  library.
- Selection persists in `settings.json` under a new key
  `consensus_observer_labels: list[str]` (see §6).
- Changing the selection re-runs eligibility + auto-match.

### 4.2 Grouping inversion

Replace `_eligible_groups()` semantics. **Old:** group key
`(patient_id, source_label)`, members = same-label RTSSes. **New:** group key
`patient_id`, members = RTSSes whose `source_label ∈ selected_observers`.

```python
def _eligible_groups(self) -> dict[str, list[RTSTRUCTEntry]]:
    """{patient_id: [observer RTSSes]} for patients with >=2 selected-observer RTSSes."""
    out: dict[str, list[RTSTRUCTEntry]] = {}
    if self._library is None:
        return out
    observers = set(self._selected_observer_labels())
    if not observers:
        return out
    for pid, patient in self._library.patients.items():
        members = [
            r
            for ctx in patient.contexts
            for r in ctx.rtstructs
            if not r.is_synthetic_consensus and r.source_label in observers
        ]
        # One RTSS per observer per patient is expected; if an observer label
        # appears 2+ times for one patient that's a Tab-1 labelling error —
        # surface a warning row (do NOT silently double-count a rater).
        if len(members) >= 2:
            out[pid] = members
    return out
```

**Rater identity = `source_label`.** Everywhere the code currently uses
filename to identify a rater, switch to `source_label`:

- [`_auto_match_group`](../src/autoseg_evaluator/ui/tabs/build_consensus.py#L458):
  membership tuples carry the source label (or look it up by SOP UID).
- [`_build_organ_row`](../src/autoseg_evaluator/ui/tabs/build_consensus.py#L591):
  show `source_label` (the observer name) instead of filename.
- [`_compute_inter_manual_rows`](../src/autoseg_evaluator/ui/tabs/build_consensus.py#L969):
  `rater_masks.append((self._source_label_for(sop_uid), m))` instead of
  `_rtstruct_filename_for`. The matrix columns `rater_a` / `rater_b` then read
  "Observer A" / "Observer B" consistently across all patients.

### 4.3 Ripple changes (group key 2-tuple → patient_id)

Every site that destructures `(pid, label)` updates to a single `pid`:

| Site | Change |
|---|---|
| `_group_drawers: dict[(pid,label), …]` | → `dict[pid, …]` |
| [`_mint_synthetic_uid(pid, source_label)`](../src/autoseg_evaluator/ui/tabs/build_consensus.py#L781) | → `_mint_synthetic_uid(pid)` — one consensus per patient. Token = `f"{pid}\|consensus"`. |
| [`_register_consensus_for`](../src/autoseg_evaluator/ui/tabs/build_consensus.py#L689) | keys become `list[str]` (patient ids) |
| Group-list items | one row per patient; tooltip lists the observer labels + files |
| Inter-observer batch loop ([`build_consensus.py:882`](../src/autoseg_evaluator/ui/tabs/build_consensus.py#L882)) | iterate patient ids; stamp rows with `patient_id` only (the `source_label` column in the results becomes redundant — the rater columns carry observer identity) |

### 4.4 Session-schema migration

**File:** [`src/autoseg_evaluator/data/session.py`](../src/autoseg_evaluator/data/session.py)
+ [`build_consensus.py` `session_state` / `apply_session_state`](../src/autoseg_evaluator/ui/tabs/build_consensus.py#L136).

The `consensus_groups` payload currently carries a `source_label` per group
(the shared manual label). Under the new model a synthetic consensus has many
constituent labels, so:

- `session_state()` writes `observer_labels: list[str]` per group instead of a
  single `source_label`, plus the existing `patient_id` / `for_uid` /
  `synthetic_sop_uid` / `organs[]`.
- `apply_session_state()` reads the new shape; **keep a back-compat branch**:
  if a loaded group has the old `source_label` key and no `observer_labels`,
  treat `[source_label]` as the observer set so v2.3-era sessions still load.
- Bump the session schema comment to v4 (consensus payload reshaped). The
  loader already tolerates missing keys defensively.

### 4.5 Phase 2 tests

- `_eligible_groups`: with observers `{A,B}` selected, a patient with A+B+Limbus
  yields a 2-member group (Limbus excluded); a patient with only A yields none.
- Duplicate observer label on one patient → group still forms but a warning is
  recorded (assert the warning, assert no double-count in pairwise rows).
- Inter-observer rows label raters by source label, not filename.
- Session round-trip with the new `observer_labels` payload restores the
  synthetic consensus; an old-schema payload with `source_label` still loads.

## 5. Phase 3 — Editable drawers + unmatched tray (B1/B2)

**File:** [`src/autoseg_evaluator/ui/tabs/build_consensus.py`](../src/autoseg_evaluator/ui/tabs/build_consensus.py)

### 5.1 Unmatched tray (B2)

Today single-rater / unclustered ROIs are silently dropped at
[`build_consensus.py:539-540`](../src/autoseg_evaluator/ui/tabs/build_consensus.py#L539).
Instead, collect them into a per-patient **unmatched tray** rendered below the
organ rows:

```
─ Unmatched (not in any 2+ bucket) ──────────────────────────
  • Cord            (Observer C, ROI #14)   [drag → bucket]
  • Brainstem_PRV   (Observer A, ROI #9)    [drag → bucket]
```

`_auto_match_group` returns `(kept_buckets, unmatched_list)`; the renderer
shows both.

### 5.2 Editable drawers (B1)

- Organ rows ([`_build_organ_row`](../src/autoseg_evaluator/ui/tabs/build_consensus.py#L591))
  become **drop targets**; tray items and bucket rows become **drag sources**
  (reuse the `OrganDrawer` drag-drop pattern already in
  [`ui/widgets/organ_drawer.py`](../src/autoseg_evaluator/ui/widgets/organ_drawer.py)).
- Supported moves: tray → bucket, bucket → other bucket, bucket → tray
  (remove a rater from an organ), and "new bucket from tray item".
- A bucket that drops below 2 raters after an edit is flagged (amber "single
  rater — excluded from STAPLE") but **not** auto-deleted, so the user can drag
  a second rater in.

### 5.3 Lock-on-edit

- A new per-patient flag `self._manual_edited: set[str]` (patient ids).
- The moment a group is hand-edited, add its pid to the set and show an
  **"edited — auto-match disabled"** badge + a **"Reset to auto-match"** button
  on that group.
- [`_on_threshold_changed`](../src/autoseg_evaluator/ui/tabs/build_consensus.py#L556)
  skips re-clustering any pid in `_manual_edited`. "Reset to auto-match" removes
  the pid from the set and re-runs `_auto_match_group`.
- Manual layout must persist: extend the session `consensus` snapshot to store
  the edited bucket composition per patient (so a saved session reopens with
  the hand-curated grouping, lock flag included).

### 5.4 Phase 3 tests

- Dragging a tray ROI into a bucket adds it; the bucket's rater count rises.
- Dragging a rater out of a bucket drops it to the tray; a 1-rater bucket gets
  the amber flag and is excluded from generation.
- Editing a group sets the lock; a subsequent threshold change does **not**
  re-cluster that group but **does** re-cluster an un-edited group.
- "Reset to auto-match" clears the lock and restores the fuzzy grouping.
- Session round-trip preserves a hand-edited grouping + lock flag.

## 6. Settings & session schema summary

### `settings.json` (new keys)

**File:** [`src/autoseg_evaluator/utils/settings.py`](../src/autoseg_evaluator/utils/settings.py)

```python
DEFAULTS = {
    # … existing …
    "custom_source_labels": {},        # unchanged — SOP UID → label (= observer name)
    "consensus_observer_labels": [],   # NEW — list[str] of labels designated as observers
}
```

No new key is needed for rater aliases — the source label *is* the alias.

### Session JSON (`consensus_groups` reshape, schema v4)

Per group:
```jsonc
{
  "patient_id": "...",
  "for_uid": "...",
  "synthetic_sop_uid": "...",
  "observer_labels": ["Observer A", "Observer B", "Observer C"],  // was: "source_label"
  "manual_edited": true,                                           // NEW (Phase 3)
  "organs": [ { "roi_number": 1, "roi_name": "...",
                "constituents": [ {"sop_uid": "...", "roi_number": 14}, ... ] }, ... ]
}
```

Back-compat: a group with the old `source_label` key and no `observer_labels`
loads as `observer_labels = [source_label]`.

## 9. Phasing & shippability

Each phase is independently shippable and independently testable:

1. **Phase 1 (Tab 1)** — 3 columns + scanner fields + "Select similar".
   Self-contained; immediately useful for any multi-source cohort. Low risk.
2. **Phase 2 (Tab 2)** — observer selection + grouping inversion + rater =
   source label. The core behavioural change; medium risk (touches the
   consensus core + session schema).
3. **Phase 3 (B1/B2)** — editable drawers + unmatched tray + lock-on-edit.
   Largest UI surface; orthogonal to Phases 1–2.

Recommended release cadence: Phase 1 → v2.4.0, Phase 2 → v2.5.0,
Phase 3 → v2.6.0 (or bundle 1+2 into v2.4.0 if validated together).

---

## 10. Out of scope (explicitly deferred)

- Multiple distinct consensuses per patient from different label sets.
- Geometric / spatial fallback organ matching (name-only for now; the
  unmatched tray + manual drag covers the failures instead).
- Auto-detecting observer labels from folder structure (the user assigns them
  in Tab 1; "Select similar" assists but does not auto-decide).
- Anything touching the metric/STAPLE math — this redesign is purely about
  *which* contours feed the consensus and *how raters are identified*.
